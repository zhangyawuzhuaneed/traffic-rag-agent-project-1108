# 后端规格驱动开发（Backend SDD）

> 一句话原则：**Agent 负责在约定边界内把活干快，人负责决定做什么、不做什么、怎么算做完。**

## 0. 三条不可协商的原则

1. **规格先于实现。** 没有用户确认过的 `SPEC`，不允许修改任何源码文件。
2. **验证先于宣告完成。** 「我觉得改好了」不算完成；必须有可复现的验证结果。
3. **修复上游而非下游。** 输出错了，优先改规格 / 上下文 / 约束，然后重跑，而不是在错误代码上打补丁。

## 1. 边界判定

| 走本流程 | 不走本流程 |
|---|---|
| 新增或修改 API 契约 | 改一个变量名、修 typo |
| 领域状态机 / 业务规则变化 | 纯注释、README 文案 |
| 跨 2 个以上模块 / 服务 | 只读分析、解释代码 |
| 表结构、索引、数据迁移 | 一次性临时脚本（需声明「一次性」） |
| 影响认证、权限、资金、幂等 | 用户明确说「直接改，不用规格」 |
| 重构、性能改造、疑难 Bug | |

**判定不明时，默认走本流程。** 多一份 10 分钟的规格，比回滚一次便宜得多。

## 2. 工作流

```
S0 装载上下文 → S1 产出规格 → S2 人工评审【硬卡点】
     → S3 复述计划 → S4 受控实现 → S5 验证 → S6 知识回写
```

### S0 · 装载上下文

**动作**（只读，不改文件）：
1. 读仓库根的 `AGENTS.md` / `CLAUDE.md`（若存在），取项目约定与历史坑点。
2. 定位任务涉及的模块：入口、领域层、数据层、配置、现有测试。
3. 找出**可复用的既有实现**——不许重复造轮子。
4. 确认当前工作目录、运行环境、依赖版本是否可复现。

**产出**：一段不超过 10 行的「现状摘要」，列出现有实现 / 约束 / 待澄清问题。

> 上下文按需取用，不要一次性把整个仓库塞进窗口。需要更多细节时，用工具现场补。

### S1 · 产出规格

按 §3 模板写 `SPEC`，保存到 `docs/specs/<任务简称>.md`。

硬性要求：
- **Goal / Non-goals 必须同时写**：不写「不做什么」，Agent 一定会过度实现。
- **Acceptance criteria 必须可被测试验证**。「安全地处理鉴权」不合格，「过期 token 返回 401」才合格。
- **Interfaces 必须给出具体输入输出**，含错误码、超时、幂等语义。
- 需求有歧义 → 列入 `Open Questions`，**带着问题停下来问人**，不许自行脑补填平。

### S2 · 人工评审【硬卡点 · 不可跳过】

输出规格，明确请求确认后**停止**，等待用户回复。

禁止：一边说「如有不妥请告知」一边继续写代码。没收到确认就是没通过。

用户提出修改 → 回到 S1 改规格，而不是记在心里后面「顺手调整」。

### S3 · 复述计划

确认后，先给出计划再动手：
- 要改的文件清单（逐文件写清改什么）
- 复用的既有能力
- 识别到的风险与回滚方式
- 验证手段

计划与规格冲突时，以规格为准。

### S4 · 受控实现

- 按计划逐文件改，**不越过 Non-goals 边界**。
- 遵循仓库既有模式：包结构、命名、异常、日志、配置获取方式。
- 每完成一个可验证的增量就跑一次反馈（编译 / 单测 / lint）。
- 发现规格本身有问题 → **停下来回到 S1**，不要在代码里悄悄绕过去。

### S5 · 验证

按 §5 清单逐项跑，把**真实命令与真实输出**贴出来，不许只写「测试通过」。

任一项失败 → 修复后重跑；修不了 → 明确列出「未通过项 + 原因」，不许隐瞒。

### S6 · 知识回写

把本次新学到的约束、反复踩的坑、新确认的约定，写回 `AGENTS.md` 的「已知坑点」。
目标：**同一个错误，整个仓库只犯一次。**

## 3. 规格模板（复制即用）

```markdown
# SPEC: <一句话任务名>

## Goal
<系统要达成什么，1~3 句。写用户可见行为，不写实现方案。>

## Non-goals
- <本迭代明确不做的事>
- <明确不改动的范围>

## Context
- 涉及模块：<文件 / 服务 / 表>
- 可复用的既有实现：<具体类或函数>
- 环境 / 依赖前提：<版本、配置项、启动目录等>

## Constraints
- <技术约束：必须复用某接口、不得引入新依赖、兼容既有协议>
- <非功能约束：超时、并发、幂等、事务边界、数据量级>
- <安全约束：鉴权、脱敏、输入校验>

## Interfaces
< METHOD /api/path or 方法签名 >
  request:  { ... }        # 含字段类型与必填性
  response: { ... }        # 成功与失败分别给出
  errors:   400 / 401 / 404 / 409 / 5xx 各自的触发条件
  idempotency: <重复请求的语义>
  timeout / retry: <明确值>

## State & Data
- 状态流转：<若涉及状态机，列出状态与迁移条件>
- 数据变更：<表 / 字段 / 索引 / 迁移方式 / 回滚方案>

## Acceptance Criteria
- [ ] <可被自动化验证的具体行为>
- [ ] <边界：空输入、None、超长、重复、并发>
- [ ] <失败路径：外部依赖超时、数据不存在、权限不足>
- [ ] <回归：既有行为不受影响>

## Done When
- [ ] 上述验收项全部有对应测试且通过
- [ ] 编译 / lint 通过
- [ ] 无新增敏感信息（Key、密码、token）入库
- [ ] 文档与规格同步更新

## Open Questions
- <需要人决策、Agent 不得自行假设的问题>
```

> Java 微服务场景追加：事务边界与传播行为、幂等键设计、下游超时与降级策略、
> 消息重复消费处理、错误码与现有枚举的对应关系、灰度 / 回滚开关。

## 4. 硬性禁止（Never）

未经用户**逐项**明确授权，不得：

- 执行数据库 `DROP` / `TRUNCATE` / `DELETE` 或无 review 的迁移脚本
- `git push --force`、`rebase` 共享分支、删除分支
- 修改 CI/CD、部署配置、Dockerfile、监控告警
- 改动认证 / 鉴权层（除非本次任务就是它，且逐行评审）
- 新增第三方依赖或升级大版本
- 把 Key / 密码 / token 写进源码、日志或提交
- 用「跳过测试」「加 `@Ignore`」「降级校验」的方式让验证变绿
- 在未确认规格时改写与任务无关的代码「顺手优化一下」

## 5. 验证清单

| # | 检查项 | 证据 |
|---|---|---|
| 1 | 编译 / 构建通过 | 贴命令与输出 |
| 2 | 所有 Acceptance Criteria 有对应测试 | 列出用例名 |
| 3 | 边界与失败路径覆盖 | 空值 / 重复 / 超时 / 越权 |
| 4 | 既有测试全绿（回归） | 全量测试输出 |
| 5 | 错误处理与资源释放 | 连接 / 流 / 事务是否关闭 |
| 6 | 安全 | 输入校验、注入、敏感信息、密钥泄漏扫描 |
| 7 | 与规格一致性 | 逐条对照 Acceptance 打勾 |
| 8 | diff 复核 | 无越界改动、无调试残留 |

## 6. 各阶段输出契约

| 阶段 | 交付物 | 谁批准 |
|---|---|---|
| S0 | 现状摘要（≤10 行）+ 待澄清问题 | — |
| S1 | `docs/specs/*.md` 规格文件 | — |
| S2 | 规格 + 明确的确认请求，**然后停止** | **人** |
| S3 | 文件清单 + 风险 + 回滚方式 | 人 |
| S4 | 代码改动（逐增量） | — |
| S5 | 命令与输出、未通过项清单 | 人 |
| S6 | 更新后的 `AGENTS.md` | — |

## 7. 反模式与纠正

| 反模式 | 纠正 |
|---|---|
| **Yes-man**：用户提了坏方案，照做不误 | 开工前先给 2~3 个方案与取舍，指出风险 |
| **Plausible-but-wrong**：能编译、测试绿、逻辑错 | 领域约束写进 Constraints；人工逐行审 diff |
| **Spec drift**：多轮迭代偏离初衷 | 每 3 轮重述一次 Goal 与 Non-goals |
| **Context dilution**：长会话越聊越糊 | 新任务开新会话；结论落盘到文件，不留在对话里 |
| **自证清白**：Agent 自己写测试验证自己的理解 | 验收标准由人在 S2 敲定；契约测试独立于实现 |
| **过度委派**：什么都交给 Agent | 确定性强、可脚本化的事直接写脚本，更快更便宜更可控 |
