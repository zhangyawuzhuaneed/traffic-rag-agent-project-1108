# 七天学习路线 · 从 Java 后端到 AI 应用开发

> 前提：你熟悉 Spring Boot、REST、Maven、JUnit，但不熟悉 LLM。
> 这个项目的定位是**把新概念挂到你已有的知识结构上**，不是从零学 AI 理论。
> 每天 1~2 小时，每阶段都有可验证的产出，别只看不敲。

---

## Day 1 · 先跑起来，建立「AI 也是一种依赖」的直觉

**读**：`README.md` → `config/KeyGuard.java` → `api/AiController.java`

**做**：
1. 配好 `ZHIPU_API_KEY`，`./mvnw spring-boot:run`，看到 `知识库就绪：... 共 N 块`。
2. 用 curl 打 `/api/rag/ask`，问「CO 浓度 78ppm 怎么处置」。
3. 清空 Key 再启动，观察 `KeyGuard` 抛出的可读错误。

**验收**：能说清「为什么 AI 客户端需要启动守卫，而数据库连接池天然就有」。
把 Controller 当成普通 REST 接口看——到这里你应该发现，除了注入的对象变了，分层没有任何新东西。

**练习**：把 `/api/status` 增加一个字段返回 `spring.ai.openai.base-url`。

---

## Day 2 · 吃透 RAG 离线链路（这是最"后端"的一天）

**读**：`rag/ChineseTextSplitter.java` → `rag/IngestState.java` → `rag/KnowledgeBase.java`

**做**：
1. 跑 `./mvnw test -Dtest=ChineseTextSplitterTest`，故意把 `chunkSize` 改成 50 再看切块数变化。
2. 改一个知识库 `.md` 的某个数字，重启，观察日志里该文件从 `skip` 变成 `index`。
3. 调 `POST /api/admin/reindex?force=true`，然后看 `data/ingest-state.json` 的结构。

**验收**：能画出「加载 → 切块 → 向量化 → 入库 → 落盘」五步，并说明
**为什么必须先删旧块再写新块**（答案：只追加会让新旧内容同时被召回）。

**练习**：把 `IngestState` 的 key 从「文件名」改成「相对路径」，解决子目录同名文件互相覆盖的问题（见 04 文档 Q7）。

---

## Day 3 · 吃透在线链路与防幻觉

**读**：`rag/RagService.java` → `application.yml` 的 `app.rag.*`

**做**：
1. 先用 `/api/rag/search?question=...` 只看召回，确认 top-4 命中了哪几块、来自哪个文件。
2. 问一个知识库里没有的问题（如「公司老板是谁」），确认它明确拒答。
3. 把 `SYSTEM_PROMPT` 里的「不得用常识补充数字」删掉，再问同一个超纲问题，观察幻觉长什么样。
4. 把 `top-k` 从 4 改成 1，看答案是否开始漏信息。

**验收**：能说清**低 temperature + 提示词约束 + 检索兜底**这三层防幻觉各自防的是什么。
注意：RAG 不会消除幻觉，只是把「凭空编」变成「有据可查」，所以要做来源溯源。

**练习**：在 `Answer` 里加一个 `contextChars` 字段，记录本次实际塞给模型的 context 长度。

---

## Day 4 · Tool Calling：让模型自己决定调哪个接口

**读**：`agent/TunnelTools.java` → `agent/IncidentAssistant.java`

**做**：
1. 问 `/api/agent/chat`：「K12+300 现在 CO 多少？该采取什么措施？」，看日志里的 `[TOOL]` 调用顺序。
2. 把 `TunnelTools` 里 `queryDeviceStatus` 的 description 改成一句含糊的话（如「查数据」），
   再问同样的问题，观察模型是否还在该调的时候调用。**改完记得改回来。**
3. 问一个不需要实时数据的问题（「隧道常态限速多少」），确认它没乱调工具。

**验收**：能说清 **RAG 查静态知识 / Tool 查动态事实** 的分工，以及
「把实时数据塞进向量库」为什么是反模式（刚入库就过期 + 污染检索）。

**练习**：新增一个 `@Tool` 方法 `queryWeather(stake)`，返回模拟天气，并在描述里写清何时该调。

---

## Day 5 · 结构化输出与会话记忆：把 AI 接回业务系统

**读**：`agent/IncidentReport.java` → `IncidentAssistant.assess()` → `config/ChatMemoryConfig.java`

**做**：
1. 调 `/api/agent/assess`，确认返回的是字段齐全的 JSON，而不是一段自然语言。
2. 用同一个 `conversationId` 连续问两句（第二句用「那它现在呢？」这种依赖上文的问法），验证记忆生效。
3. 换个 `conversationId` 问同样的问题，确认上下文被隔离。
4. `DELETE /api/agent/chat?conversationId=u1` 后再问，确认已清空。

**验收**：能说清「有了类型才能做校验、事务、审计、幂等」，以及
ChatMemory 内存实现与传统 Session 放内存的**完全相同的权衡**（重启丢失、多实例不共享）。

**练习**：给 `IncidentReport` 加一个 `estimatedClearanceMinutes` 字段，观察模型遵从率是否下降
（字段越多、嵌套越深，遵从率越低——这是个真实的工程约束）。

---

## Day 6 · 评估集：给不确定的输出建立可比较的基线

**读**：`src/test/resources/eval-cases.json` → `EvalCaseIntegrityTest.java` → `RagIntegrationEvalTest.java`

**做**：
1. 跑 `./mvnw test`，看纯单元全绿、20 条集成评估被跳过。
2. 故意把某条用例的期望关键词改成知识库里没有的词，跑测试，看自检如何拦下「编造的评估集」。
3. 设 `RUN_INTEGRATION=true` 跑一次完整评估，记下命中率基线。
4. 改 `chunkSize` 或 `topK`，再跑一次，用数字判断改动是变好还是变坏。

**验收**：能解释「为什么不能给 LLM 输出写 `assertEquals`」，以及
**关键词命中率 → 语义相似度 → LLM-as-Judge** 这条评估能力的演进路径与成本差异。

**练习**：补 5 条你自己的用例（含至少 1 条拒答），跑自检确认关键词真的在源文档里。

---

## Day 7 · 工程化与面试表达

**读**：`AGENTS.md` → `.github/workflows/ci.yml` → `docs/03-面试手册.md` → `docs/04-已知问题与演进.md`

**做**：
1. 用 `AGENTS.md` 当上下文，让 AI 编码助手做一次改动，观察它是否遵守「硬性禁止」。
2. 把本次新踩的坑追加到 `AGENTS.md` §8。
3. 合上电脑，用 3 分钟口述这个项目：场景 → 三条链路 → 三个工程难点 → 两个局限 → 下一步。
4. 对着面试手册的 20 个追问自测，答不上来的回到对应代码再读一遍。

**验收标准**：能在 30 秒内，对任意一处 AI 给出的改动说清「哪里对、哪里可能错、该跑什么验证」。
做到这一点，你就已经不是「会用工具的 Java 开发」，而是能主导 AI 应用落地的工程师了。

---

## 一条贯穿始终的学习原则

**别让 AI 替你写这个项目的第一版理解。** 每个模块先自己读、先猜它为什么这么写，
再让 AI 解释或改造，然后逐行核对。全交给它，代码能跑，但认知留在它那边。
